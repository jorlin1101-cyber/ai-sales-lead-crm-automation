# Day Review - 2026-05-26

## 1. 字段命名不一致

### 问题

PRD、CRM schema 和 Python 输出中曾经出现字段命名不一致的问题，例如 `company`、`company_name`、`summary`、`lead_summary` 混用。

### 修复

统一项目中的核心字段命名，最终以 CRM schema 为标准，使用 `company_name` 和 `lead_summary`。

### 经验

在自动化工作流中，字段命名就是数据契约。字段不一致会导致后续 n8n 映射失败、Notion 写入错误，或者生成脏数据。

## 2. 无效线索和垃圾线索混在一起

### 问题

最初的 PRD 把字段缺失型无效线索和内容垃圾型低价值线索放在同一类里处理。

### 修复

将两类线索拆开处理：

- 缺少必要字段的线索，由 Python 基础校验判断为 invalid，并跳过 AI 分析。
- 必填字段完整但内容疑似垃圾信息的线索，继续进入 AI 分析，由 AI 判断意向等级、线索类型和跟进建议。

### 经验

字段完整性适合用确定性代码处理。内容质量、销售意向、spam 风险这类语义问题，更适合交给 AI 分析。

## 3. 字符串处理不安全

### 问题

原始代码直接对字段使用 `.strip()`。如果输入数据是 `None`、数字或布尔值，程序可能直接报错。

### 修复

新增 `safe_str()` 函数，将外部输入安全转换为字符串，并去除前后空格。

### 经验

真实业务数据不会永远干净。自动化系统的预处理层必须具备防御性，先保证流程不崩溃，再进入后续 AI 分析和 CRM 写入。

## 4. 来源字段需要标准化

### 问题

测试数据中可能出现空 source 或未定义 source，例如 `RandomApp`。如果直接写入 CRM，会影响后续渠道分析和销售归因。

### 修复

新增 `normalize_source()`，只允许标准来源进入系统。空值或非法来源统一标记为 `Unknown`。

### 经验

source 字段不是装饰字段，它会影响渠道质量分析、自动化分流和后续业务判断。`unknown_source_count` 可以作为监控上游数据质量的指标。

summary:今天最重要的技术收获是：自动化系统必须先建立稳定的数据契约。PRD、CRM schema、Python 输出字段必须完全一致，否则后面的 n8n、Notion 和 AI 节点都会映射失败。Python 清洗层负责确定性处理，例如字段标准化、None 防崩溃、source 归一化和基础校验；AI 层负责语义判断，例如 spam、意向等级和跟进建议。状态字段的价值是让每条 lead 在流程中有清晰位置，方便后续追踪、调试和恢复。
