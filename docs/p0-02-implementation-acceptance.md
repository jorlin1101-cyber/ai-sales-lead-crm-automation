# P0-02 开发与验收记录

日期：2026-10-05。开发分支：`codex/p0-02-answerability-eval`。状态：开发验收进行中；以下记录将在最终运行后更新。

本次实现依据 [P0-02 设计](p0-02-answerability-design.md)。新增业务标签及人工语义裁定的状态与工程测试分开记录，不把工具能运行解释成实际回复全部正确。

## 已实现的能力

- 将客户问题拆成必答要点，区分全部可答、部分可答和全部不可答；单独区分客户信息不足、缺资料、实时供应未知、资料冲突、过期和有效性未知。
- 通过真实对话入口回放 24 场景、每种模式 36 轮；记录真实检索、回复上下文、客户事实及来源、每个模型阶段和回退。
- 规则模式拥有 54 个真实检索路径检查单元；模拟模式不重复计入检索成绩。真实模型调用为 0。
- 检查每轮回复及额外业务承诺；未完成语义裁定时保持待复核；模型执行失败与可观察的回退安全表现分开。
- 先保存原观察再评分，封存报告不允许覆盖；新协议、可信策略、基线和自动检查与 P0-01 并行。
- 对已受信、实际语义输入完全相同的回归结果复用原人工判断，并留下派生证据；变化、缺证据、阶段错误以及首次接纳不得使用此规则放行。

## 范围和当前业务状态

生产线索评分、数据库结构、CRM 写入、客户工作台及线上回复策略未做功能改造。新模块是检查和定位能力，修复业务问题仍按 P0-03/04/05 推进。

[新增业务复核包](p0-02-business-review-pack.md)包含 24 场景、36 轮、7 个合成知识快照，中文 10 / 英文 10 / 混合语言 4；单轮三态各 6 例。所有样本均为合成公开回归材料，不包含真实客户资料。新增案例确认与具体输出复核是两个独立步骤。

当前案例仍为 draft，已向用户提交具体复核包征求业务确认。开发/销售双真实身份的具体输出语义审核尚未完成；系统没有生成虚假的审核人、审核时间或通过结论。新正式基线尚未接纳。P0-01 的 11 项业务缺陷保留。

## 如何运行

以下命令在仓库根目录执行，使用项目锁定的虚拟环境。每次输出目录必须是新目录；已有封存报告不会被覆盖。默认禁止外部网络及真实模型调用。

```powershell
.venv\Scripts\python.exe scripts/run_answerability_eval.py run --mode rule_only --out data/runtime/p002-my-run/rule_only
.venv\Scripts\python.exe scripts/run_answerability_eval.py run --mode mocked_model --out data/runtime/p002-my-run/mocked_model
.venv\Scripts\python.exe scripts/run_answerability_eval.py check --gate inventory --run data/runtime/p002-my-run/rule_only --run data/runtime/p002-my-run/mocked_model --candidate-sha <本次受测提交完整SHA> --out data/runtime/p002-my-run/inventory
.venv\Scripts\python.exe scripts/run_answerability_eval.py review-template --run data/runtime/p002-my-run/rule_only --run data/runtime/p002-my-run/mocked_model --out data/runtime/p002-my-run/review-draft.json
```

`inventory` 只表示记录完整，可含业务失败和待复核；`regression` 必须使用当前可信主分支的已接纳基线；`behavior` 必须满足两模式所有必需业务断言。三个检查都不是产品上线许可。返回码：0 满足所选检查，1 业务失败/待复核，2 必需输入或执行缺失，3 信任或可比性无效。

运行目录中的 `summary.md` 是中文说明；`observations.jsonl` 保存原始观察；`assertions.jsonl`、`retrieval.json`、`metrics.json` 保存细项；`manifest.json` 与 `COMPLETED` 检验完整性。后续审核和比较放在旁边，不回写封存文件。

## 正式接纳尚需的证据

正式接纳需要：新增案例业务确认、具体输出真实语义审核、新工作流在 GitHub 的实际成功产物及来源核验、可信主分支中的批准绑定、独立两模式基线、必需检查配置和实际首次回归。每一步都由工具检查，不以手工改 JSON 状态代替。

后续若业务输出或其依据变化，严格审核复用会失效，仍需新审核；若只是内部随机标识变化且业务语义完全一致，可记录派生判断。该能力不降低原审核身份要求，不自动推进基线，也不覆盖曾经失败的记录。
