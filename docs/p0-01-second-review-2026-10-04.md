## 4 必须补充的设计条款

### R01：为真实模型单独定义评分规则，避免成功判错、兜底冒充模型成功

**性质：已通过回放证明的兼容性问题。对应原方案第 98、238、240、341 行。** 原有四例的业务要求应保留，但原测试的实现断言不能不加区分地搬入 live。

证据：现有 [会话测试第 65 行](<D:/Python project/ai-sales-lead-crm-automation-next/tests/test_conversation_eval.py:65>)要求生成方式必须是 `rag_grounded_template`；正常模型生成在 [conversation_llm.py 第 267 行](<D:/Python project/ai-sales-lead-crm-automation-next/src/lead_cleaner/services/conversation_llm.py:267>)标为 `llm_grounded`。

| 本次模拟条件 | 旧检查的结果 | 能得出的结论 |
| --- | --- | --- |
| 原 4 例均成功经过模拟模型边界 | 4/4 因生成方式断言失败；其中川西产品、云南亲子两例其余旧断言全部通过 | 至少这两例存在明确的模式断言误判；不能据此宣称四例的所有业务内容都正确 |
| 原 4 例的模型调用均模拟超时 | 4/4 旧检查全部通过；trace 显示理解超时回退，生成未调用 | 旧检查能证明模板兜底符合原要求，不能证明模型答对 |

**修改办法：**

- 共享输入、客户事实、必须覆盖的业务内容和证据要求；按模式选择 `grading_profile`。规则模式保留模板回归要求，live 不再强制模板生成方式或不必要的逐字表达。
- 每个目标阶段记录 `expected_to_run`、调用次数、成功/回退/未调用及原因。复用已有 `llm_trace`，在评测端补充缺失的调用记录。
- 同时输出“整个流程是否给出符合要求的结果”和“目标模型阶段是否成功并满足质量要求”。如果模型超时但模板可用，前者可通过，后者不能通过。
- 模型供应方超时属于模型阶段执行错误；业务保护明确拒绝不合法候选，则可在事先定义的边界安全断言中通过。不能一律把异常当作拦截成功。
- 阶段不适用须来自冻结的案例协议。例如该案例本就只测理解，不要求生成；不能在模型没有调用后临时改成不适用。
- 模型调用成功只证明执行成功。回复仍须检查信息是否完整、有无无依据承诺；自然表达的语义判断按人工规则复核。

付款比例、期限、人数等原有业务要求继续保留。改变措辞容忍度，不等于允许漏掉业务信息。代码判分对开放表达容易过于僵硬，应使用合适的分层判断；[Anthropic 2026 年评测指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)也区分执行轨迹、结果及不同类型的判分器。

### R03：采用两个比较基准，阻止“修好后又坏”

**性质：回归规则存在遗漏。对应原方案第 297、299、350 行。** 原文对固定初始基线比较、精确豁免历史问题的方向正确，但尚未定义修复后的豁免如何失效。

例子：初始版 F01 失败 → 版本 A 修好 → 版本 B 再次失败。如果 B 永远只对最初版本比较，可能仍被当作已知失败而放行。

**修改办法：**

| 参照 | 用途 | 更新方式 |
| --- | --- | --- |
| 初始冻结基线 | 回答相比项目起点改善多少 | 永久保留，不覆盖 |
| 最新已接受基线 | 回答这次改动有没有破坏已经做到的事 | 仅在固定协议下验收并获准接纳后推进，保留前序记录 |

- 首份参照由完整执行并经业务复核的 inventory 报告初始化，允许已登记的业务失败；后续通过 regression 并经接纳才推进最新参照。成为回归参照不要求已满足 release，避免尚有待修问题就无法建立基线。
- 缺陷登记增加 `status=open/resolved`、`resolved_commit`；已解决缺陷不得自动恢复旧豁免。
- 最新已接受版本为 pass，候选为 fail/error/not_run/needs_review 时，须阻断相应必测断言，不能退回最初版本找豁免。
- 生成候选报告与接纳为新基线是两步操作；普通 PR 不能自己将自己的结果升级为可信参照。
- 如果样本或评分规则升级，沿用原设计的要求：在新口径下重新评测比较对象，不能混用旧分数。

最重要的新增自测是完整跑通 `FAIL → PASS → FAIL`，最后一步必须阻断。已解决能力纳入持续回归的做法也符合 [Anthropic 对能力评测与回归评测的区分](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

### R04：明确评分规则的可信来源，避免同一改动同时降低门槛

**性质：设计需要补充的治理规则；未证明本项目已经发生过绕过。对应原方案第 149、338、350 行。** 如果普通 PR 使用自身修改后的基线、豁免和发布清单，删掉难题或新增豁免就可能使退化通过。记录散列可以说明文件变了，不能说明这种变化已经获准。

**修改办法：**

1. 普通业务 PR 的基线、历史豁免和必测清单取自明确记录的、已接受的目标分支提交。
2. 对评测器、案例标签、缺陷豁免、发布清单及 workflow 的改动，单独展示规则差异：删了哪些检查、放宽了什么、增加了哪些豁免。
3. 口径变更须按基线升级流程复核，并重测比较对象；未经接纳的结果只能标为暂定，不能自行取得发布资格。
4. 实施时核验远端必需检查和所有者审核；本地没看到 CODEOWNERS 不等于远端没有保护。

参考 [GitHub workflow 安全指南](https://docs.github.com/en/actions/reference/security/secure-use)与[分支保护说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。P0-01 只需利用现有代码审核与 CI 能力，不需要建设新的审批系统。

### R05：CI 必须实际使用锁定依赖，不能只记录锁文件

**性质：当前 CI 的具体问题。** [ci.yml 第 36 行](<D:/Python project/ai-sales-lead-crm-automation-next/.github/workflows/ci.yml:36>)和[第 68 行](<D:/Python project/ai-sales-lead-crm-automation-next/.github/workflows/ci.yml:68>)仍执行 `pip install -e ".[dev]"`，未使用 `uv.lock`。部分依赖只有范围限制或未固定；同一代码提交不同时间运行，实际环境可能不同。

**修改办法：**

- 两个测试作业统一锁定安装，例如 `uv sync --locked --extra dev`；后续通过 `uv run --no-sync …` 使用同一环境。
- 本项目 dev 定义为 optional extra，不应误用 dependency group 参数；缓存依据包含 `uv.lock`。
- 固定并记录 Python、uv 版本和实际安装依赖清单；不能只有锁文件散列。
- 容器继续使用从同一锁文件导出的 requirements，并增加导出一致性检查。尚未证明当前 requirements 内容有差异，不应把“可能漂移”写成已经不一致。
- 独立 PostgreSQL 作业仍连接其测试服务；隔离评测 runner 仍使用自己的测试数据库，不能把两者配置混在一起。

[uv 官方文档](https://docs.astral.sh/uv/concepts/projects/sync/)说明 `--locked` 会检查项目与锁文件的一致性，`--frozen` 会跳过锁文件是否需要更新的检查；二者不能混为一谈。具体接入参考 [uv 的 GitHub Actions 指南](https://docs.astral.sh/uv/guides/integration/github/)。这是把 S0 本地的可复现条件延伸到 CI。

### R06：把“报告完整性校验”写成可以执行的协议

**性质：原设计已有原则，仍缺协议细节。对应原方案第 151、272 行。** 原文已要求同候选提交、正式报告、同必测清单和完整性校验；应保留，不能说原方案允许随便拼接。但仅有完成标记与相同 SHA 仍不足够。

**修改办法：**

- 每份结果的唯一键为 `(mode, case_id, checkpoint, assertion_id, trial_id)`；非重复模式使用约定的单次 trial。
- 根据冻结的适用清单预先展开应有结果集合；收尾时核对集合，拒绝缺项、重复项、未知项和临时减少的必测项。
- 最终 manifest 列出结果文件路径、大小、散列、协议版本、运行状态；写入后再写完成标记。读取和聚合时重算，发现内容不一致立即失败。
- manifest 不把自身散列递归写入自身；完成标记或外层索引可以引用其散列。文件散列用于完整性，可信 CI 来源用于确认报告从哪里产生，二者分开。
- 正式发布报告记录实际受测提交、PR head、base、workflow run ID 和 attempt。单次报告封存后上传；上传返回的 artifact ID、digest 及运行来源由聚合步骤写入独立外层索引，原报告不再回填修改。发布只读取指定可信运行的产物；本地报告仍可用于开发比较。
- 默认 PR workflow 可能测试合并提交，`tested_commit` 应记录真正被执行的代码，不能直接冒写为 PR head。合并后的候选提交不同，则按同候选提交规则重新生成所需报告。

[GitHub artifact 文档](https://docs.github.com/en/actions/tutorials/store-and-share-data)说明下载时摘要不匹配可能只给警告；发布检查须将不匹配转为失败。PR 提交语义参考 [GitHub 事件文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)。

不要求 P0-01 增加数字签名平台。唯一结果目录、文件散列、精确覆盖集合、可信 CI 产物和既有审核机制即可覆盖这里的主要风险。

### R07：隔离单位明确到每个案例，并验证独立命令行的断网能力

**性质：已有隔离要求需要细化；环境优先级已实测。对应原方案第 249—250 行。** 原文已经正确指出 `_env_file=None` 不会隔离进程环境，不能再把这一点当成原方案遗漏。

**修改办法：**

- 每个案例建立独立数据库、模型替身队列、客户端和可变缓存；同一案例的多轮消息共享该案例状态。
- 本次回放确认：只设置 `_env_file=None` 和 SQLite 路径，仍会继承 `CONVERSATION_DATABASE_URL`；显式传入 `conversation_database_url=None` 才能挡住该覆盖。增加哨兵配置自测，确保不会访问环境指向的业务库。
- 比较单独执行、整批执行、倒序执行的稳定结果；任一顺序不同都要调查，不通过重跑挑选成功结果。
- 独立 runner 不会自动继承 pytest 的 socket 配置；必须实现自己的外部连接拦截，并用受控替身测试。可复用现有 [离线 smoke 脚本第 41 行](<D:/Python project/ai-sales-lead-crm-automation-next/scripts/ci_offline_smoke.py:41>)的思路。
- 本机框架连接和指定测试数据库连接按模式明确允许；真实模型模式只允许配置中的目标服务，凭据和业务秘密不写入报告。

[pytest 官方文档](https://docs.pytest.org/en/stable/explanation/flaky.html)说明未隔离的状态、顺序和全局资源会造成不稳定测试。本项目的环境覆盖结论来自本轮代码回放，而非仅凭该文档推测。

### R08：首次真实模型比较前，规定重复试验与人工复核

**性质：评测协议补全；不要求 P0-01 本轮进行付费模型调用。对应原方案第 214、258、373、383 行。** 现有“模型可能波动”和“人工复核”还不能直接指导执行。

**修改办法：**

- 增加 `trial_id`、计划/完成次数、初态指纹、模型/提示词版本、每次结果和用量；比较方案使用相同案例及同一重复协议。
- 首次小规模实验可先预定每例 3 次，这是本项目预算建议，不是统计充分性保证。离线两次稳定检查与 live 重复试验分别执行。
- 每次重置会话、数据库和可变状态；关闭模型响应缓存，防止重复读取同一个答案冒充独立调用。记录提供方重试次数，预算覆盖重试，不允许突破硬限制。
- 报告展示如“该例完成 3/3 次，其中通过 2/3 次”，同时记录是否全部通过；不能只选最好的一次，也不把 3 次或 22 个固定场景解释成线上可靠率。
- 调用前检查预算是否覆盖计划。原命令的 `--max-requests 30` 是示例上限；引入重复后应重新估算理解、生成及重试次数，预算不足须缩小并升版实验协议，或报告未完成。
- 针对事实、证据支持、业务信息完整性、无依据承诺分别写判定规则和正反例。首批关键争议由开发和销售独立复核，再记录分歧与最终裁定；只有一名复核者时如实标记。
- needs_review 表示判断尚未完成或存在待裁定歧义。资料不足却明确承诺应判 fail；资料不足时恰当地说明无法确认，可以满足相应断言，不能统一判为 needs_review。
- 人工复核记录关联不可变输出散列、规则版本、角色、时间和理由。复核结论作为追加记录，不直接改写已经完成的原始报告。

重复试验和可靠性指标参考 [τ-bench 原论文](https://arxiv.org/abs/2406.12045)。[LangSmith 实验配置](https://docs.langchain.com/langsmith/experiment-configuration)同时提供重复次数和响应缓存设置，因此两者是否同时启用必须明确。判分器需要人工校准，参考 [OpenAI 评测建议](https://developers.openai.com/api/docs/guides/evaluation-best-practices)；本阶段无需立即引入另一个模型担任裁判。

## 5 可执行但不应扩大本期范围的改进

### 5.1 现有近邻案例明确变化关系

保留已有正常对照，补 `relation_type`、允许变化字段、必须保持字段。例如数字 8 改写成 eight 后人数应保持；8 明确更正为 9 后人数应更新，其它无关已确认信息应保持；本轮没提合作不代表撤回合作。

这是让案例更精确，不必为每个关系再增加场景。方法参考 [CheckList 原论文](https://aclanthology.org/2020.acl-main.442/)，不是照搬其指标或宣称论文证明本项目有相同错误。

### 5.2 固定回归集与未参与调整的样本分开

现有 22 个场景适合作为可见、可重复的回归套件，不应拆小。增加用途和曝光状态；后续取得真实脱敏案例时，按来源会话或近邻家族分组保留一部分，候选方案冻结后再看结果。

一旦某条样本用于指导修改提示词、规则或阈值，就不应再称为未见样本。反复依据同一测试反馈选方案可能产生选择偏差，参考 [Dwork 等关于自适应分析与保留集的原论文](https://papers.nips.cc/paper/5993-generalization-in-adaptive-data-analysis-and-holdout-reuse.pdf)。没有证据证明本项目已经过拟合；独立保留样本建设可放到 P0-02 或首次正式模型比较前。

### 5.3 修正 xfail 的实现表述

原设计第 328 行的“对具体断言使用 xfail”应改成“将目标断言参数化为独立测试项后使用严格 xfail”，或直接由 runner 管理已知失败。pytest 标记的单位是测试项；调用 `pytest.xfail()` 会终止当前测试，后面的断言不会执行。绑定预期异常，保留 unexpected pass 提醒，不能吞掉执行故障。[pytest 官方说明](https://docs.pytest.org/en/stable/how-to/skipping.html)

### 5.4 技术选型保持可替换

截至本次检索，OpenAI 官方已公告 Evals 平台弃用，计划 2026-10-31 转只读、2026-11-30 关闭相关 dashboard/API。因此不建议把本项目新基线绑定到该托管平台；这也不影响使用其评测方法论。[官方弃用公告](https://developers.openai.com/api/docs/deprecations#2026-06-03-evals-platform)

现有轻量本地 runner、JSONL 和版本化报告足以起步，后续需要团队界面时再评估工具。借鉴 [LangSmith 的数据集版本与拆分](https://docs.langchain.com/langsmith/manage-datasets)，无需为了这些概念立即接入其服务。评测还应记录环境资源条件；[Anthropic 2026 年关于基础设施噪声的研究](https://www.anthropic.com/engineering/infrastructure-noise)说明环境会影响测量，但其中编码基准的变化幅度不能迁移为本项目指标。
