# AI 销售线索项目分版本实施方案

日期：2026-10-04。状态：待实施的工程与产品方案。读者：项目负责人、开发者和参与验收的销售人员。

本方案将前一轮架构审查转成可以拆分提交、逐项验收的工作清单。建议以 GitHub 最新主分支建立新的本地开发副本，保留旧工作区，再按 P0、P1、P2 推进。近期围绕定制旅游 B2B 入站销售，先确保需求理解与业务承诺可信，再补齐商机、方案、报价和销售反馈，最后通过实验优化模型、检索、延迟和成本。

本文中的任务、接口、数据结构、文件和版本号，除明确标为已存在者外，均为建议设计。工程人日和质量目标为初始估计，不是已经完成的功能、实际测得的性能或交付承诺。本次只编写方案，没有同步源码、运行数据库迁移、发布版本或执行完整质量测试。

### 1.2 推荐的开发工作流

建议流程是：保留旧目录与本地修改 → 在新目录克隆 GitHub main → 创建 codex/ 功能分支 → 迁入仍需要的本地改动 → 本地实现和测试 → 推送功能分支 → PR 检查和合并。

GitHub 作为共享源码与审查记录，本地作为主要开发和验证环境。GitHub 网页编辑适合小型文字修改；本项目的数据库、Python 服务、前端和 n8n 契约联动，应在能运行完整环境的工作副本中实施。若改用云端开发环境，也须采用同样的分支、测试和 PR 流程。

本次推荐新克隆，是因为现有目录有未提交修改且两边历史分叉。新副本验证稳定后，可以继续保留两个目录，也可以另行安排目录切换；没有必要先覆盖原目录。未来新副本与远端拥有正常共同历史时，再使用常规 fetch、分支更新或独立 worktree。

### 1.3 S0 基线准备任务

负责人角色：开发负责人。工作量：1–2 工程人日，不含安装环境或外部账号等待。

1. 记录当前分支、HEAD、远端地址、已暂存/未暂存差异、未跟踪文件和本地数据库位置。用独立补丁保存源码差异，未跟踪文件另外备份；补丁不包含未跟踪文件。
2. 原目录保留；本地配置、凭据和数据库另行安全备份，不进入公开 Git，也不写进评测报告。
3. 在一个未占用的新目录克隆仓库，读取 AGENTS.md 和项目说明；记录当时的 main SHA。执行前检查目录用途和权限，避免覆盖已有项目。
4. 从该 main 创建 codex/p0-quality-baseline。逐项比较旧工作区修改；提示词修改若仍需保留，以独立小提交迁入，并验证提示词/输出契约。不要整份复制旧源码覆盖新版。
5. 将本方案及需要保留的本地文档迁入新副本。新建虚拟环境，按照新版依赖安装，使用隔离测试数据库和脱敏知识快照。
6. 运行当前 CI 对应的静态检查、离线测试、冒烟和 PostgreSQL 检查。记录真实失败、跳过与环境；不能把仓库中的历史通过数当成本次结果。
7. 基线存在失败时，判断是环境、既有缺陷还是本地改动引入；分别记录。未修复既有失败不得通过降低覆盖率或删测来掩盖。

验收：新副本基于已记录的 GitHub SHA；旧副本与补丁仍可恢复；新增本地改动来源清楚；离线演示正常；正式基线报告列明 PostgreSQL 是否实测及所有失败/跳过项。数据库兼容性未验证前，不让新版连接旧业务数据库。

回退：停止新副本，继续使用原工作区及原数据库。基线准备不要求改写远端历史，也不要求强制覆盖本地目录。

## 2 版本目标与实施原则

### 2.1 优先级与版本的对应关系

P0、P1、P2 表示实施优先级；v0.4.0 等表示建议发布包。优先级不代表所有问题都是线上事故。每个发布包可以通过多个小 PR 完成。

| 阶段 | 建议版本 | 用户能获得的结果 | 发布范围 | 工程工作量 |
| --- | --- | --- | --- | --- |
| S0 | 基线准备 | 可以从可信的新版本开始开发并保留旧改动 | 开发环境 | 1–2 人日 |
| P0 | v0.4.0 | 关键事实有证据，更正与撤回有效，资料不足能正确处理，结果可评测 | 内部使用及人工审核试点 | 18–28 人日 |
| P1 | v0.5.0 | 一笔商机可以从询盘推进到有版本的方案、报价和 CRM 反馈 | 单组织、一个目的地/客群试点 | 26–43 人日 |
| P2 | v0.6.0 | 在同等质量约束下验证准确度、人效、响应和成本改进 | 基于真实反馈逐步扩大 | 15–26 人日 |
| P3 | v0.7.0 及后续 | 根据实际客户和容量扩展平台能力 | 条件满足后单独立项 | 届时估算 |

以上按熟悉项目的开发者估算，包含实现、自测和必要文档，不包含业务标注、供应资料整理、账号等待及在线观察期。S0 至 P2 约 60–99 工程人日，另预留 20%–30% 集成与返工缓冲。个人开发应先完成 P0，再按真实收益分批推进 P1，不把全部清单视为一个固定日期的大版本承诺。

### 2.2 保留已有能力并划清职责

保留 FastAPI/Pydantic 契约、确定性 PolicyV1、混合检索、事实历史、会话 lease/fencing、消息幂等、草稿版本审核、Notion 同步核对、内部 Decimal 报价和离线演示。远端已有 PostgreSQL CI 作业，后续扩展它，不重复搭建同类基础设施。

- 模型负责提出候选事实、解释已筛选方案、生成有依据的普通文字。
- 业务代码负责事实提升规则、当前状态、产品硬约束、报价计算、版本有效性和执行权限。
- 销售负责关键冲突确认、方案与报价审核、供应确认和业务结果记录。
- 数据库保存业务事实与运行状态；CRM 按明确的字段权属交换数据。
- n8n 继续处理渠道连接和外围自动化，避免形成第二套互相冲突的核心业务规则。

初期采用模块化单体和独立 worker。暂缓微服务拆分、全量事件溯源、知识图谱平台及大量角色 Agent；这些项目进入 P3 条件评估。实际外发渠道若未来需要接入，应另有发送、退订、频率、回执和授权验收，本方案不把现有“人工已发送记录”描述成自动发送。

### 2.3 目标数据关系

客户企业 Account → 联系人 Contact → 商机 Opportunity → 多渠道 Conversation → 需求 RequirementSnapshot → 方案 Proposal → 报价 QuoteVersion → 结果 OutcomeEvent。

一次商机对应一次可独立推进的出行需求。同客户不同团期默认不同商机；跨渠道会话关联要有明确依据。P0 先在现有会话结构上修复事实契约，P1 再引入商机聚合，避免为了修正几个事实字段先重写全部数据模型。

## 3 P0 可信事实和可测质量

P0 发布目标：关键字段不能因为 JSON 合法就自动成为事实；历史意图能够被明确撤回；引用真实但含义错误的关键承诺不能被当作已核验回复；无答案和部分答案有独立评测。S0/P0 默认在本机或受控内部环境使用；非本机试点另须满足第 7.4 节的最小部署门槛。

### P0 01 冻结基线与失败案例

目标：把既有工程测试和业务质量评测分开，建立之后所有比较的固定起点。依赖：S0。负责人：开发；销售参与案例判断。工作量：2–3 人日。

实施：

1. 扩充 data/evals，并建议新增统一入口 scripts/run_quality_eval.py。报告记录代码 SHA、运行配置、知识 hash、样本版本、模型标识、提示词版本和执行时间。
2. 将已执行的三个隔离反例写为行为测试：客户说 8 人却接受 999；引用价格影响因素却声明预订确认；合作/定制和旅行社身份无法被明确更正。它们是模拟错误输出或纯函数回放，不用于计算真实模型错误率。
3. 为每类失败加入合法近邻和表达变体，例如 eight people、不是八人而是九人、明确已获得供应确认的合法声明，防止仅靠关键词封堵。
4. 输出 rule_only、模拟模型、真实模型三类报告。没有调用真实模型的报告明确标识模型质量未测。保存报告版本，历史基线不覆盖。

建议改动：data/evals、现有评测脚本、tests/test_conversation_llm.py、tests/test_conversation_business_logic.py；新增 fact_evidence 与 claim_evidence 契约测试。新名称为建议，实施时按仓库组织调整。

验收：可以复现缺口并确认合法行为；相同离线配置的结果可复现；后续修复后的差异能够落到具体样本和字段。缺陷复现可以先在分支记录预期失败，合并发布时不得留下被忽略的关键失败。

回退：本任务不改线上行为，评测入口可独立撤回；已保存证据与案例继续保留。

### P0 02 支持无答案和部分答案评测

目标：消除“每道题必有答案”的评测假设。依赖：P0-01。工作量：2–4 人日。

实施：

1. 为评测样本增加 answerability，取 answerable、partial、unanswerable；facet 记录在指定知识快照下是否可回答。
2. 完全无答案允许不存在 grade-3 文档；部分答案允许某些 facet 无直接支持。旧 18 条查询作为兼容样本保留。
3. 评测标签区分缺客户信息、缺静态知识、需要实时供应、证据冲突和资料过期。运行时退出原因由 P0-05 对接：只能依据已有可信元数据判断；P1-02 尚未提供有效期或供应确认时，返回无法验证，不能声称已识别资料过期或库存可用。
4. 检索指标只对相应的可回答部分计算。生成评测同时统计无依据作答和不必要拒答；检索到了相关文档，不自动等于可以回答。
5. 多轮案例检查每一轮的事实、状态、回复与追问，不能只检查末轮关键词。RRF 分值继续作为排序分值，不解释成正确概率。

建议改动：rag/eval_schemas.py、eval_runner.py、evaluation_report.py、data/rag_eval、tests/test_conversation_eval.py 及对应 schema/report 测试。

验收：三种可回答状态均可表达；无答案不进入必须召回答案的分母；旧样本在相同口径下结果不变。至少包含无相关资料、相关但无具体答案、部分可答、冲突和过期五类负例，并同时输出分子、分母和百分比。

回退：使用新的评测 schema 版本；保留旧报告和读取兼容层，避免通过改分母制造表面提升。

### P0 03 验证关键事实与来源的对应关系

目标：候选值必须被原文支持，才能成为当前有效关键事实。依赖：P0-01；报告对接 P0-02。工作量：4–6 人日。

实施：

1. 增加候选事实结构，建议包含字段、规范化值、原文片段及起止位置、来源消息、抽取方法版本、验证状态。验证状态与客户/人工确认状态分别保存。
2. 对人数、日期、金额、币种、每人或总额等字段建立确定性核验与规范化规则。例如 eight people 可对应 8；仅证明原文含有数字不够，必须检查数字所指对象和否定关系。
3. 未支持的复杂表达保留为待确认候选，不丢失原文，也不自动确认为真。儿童/成人分组、预算上下限等暂不能表达的情况明确待确认，后续按业务需要扩展类型。
4. 不根据当前日期擅自为客户补造年份；相对日期需有解析基准和确定性语义，歧义时追问。金额不擅自补币种或计价单位。
5. 固定 0.9 或模型自报置信度不用于自动放行。已有历史事实无完整证据时标为 legacy_unverified，不批量伪造来源。
6. 单轮和多轮复用相同的事实验证模块。P0 发布前，每个启用入口都须满足关键字段契约；尚未完成迁移的入口关闭模型自动提升或强制人工复核，不能绕过验证进入评分。

建议改动：schemas/conversation.py、schemas/policy.py、conversation_llm.py、conversation_slots.py、conversation_service.py、conversation_store.py、openai_feature_client.py、live_feature_extractor.py、lead_feature_merger.py；建议新增 services/fact_evidence.py，必要时追加兼容迁移。增加单轮与多轮入口的相同反例和合法近邻测试。

验收：8→999、CNY→USD、总价→每人价格、补造年份均不能静默进入有效关键事实；合法中英数字与明确更正可通过；规则回退仍可产生受支持事实；人工确认值不被模型静默覆盖；旧数据库升级后可读且来源关联完整。

回退：关闭模型自动提升，候选事实交给人工或经验证的规则处理。保留新事实历史，不回退为未经核验的自动确认。

### P0 04 当前意图支持更正和撤回

目标：评分根据当前有效需求计算，同时保留历史行为。依赖：P0-03。工作量：3–5 人日。

实施：

1. 为会影响评分的当前意图增加 set、replace、retract、pending 操作。未提及表示不更新，不能把默认 false 当成客户撤销。
2. 分离“历史曾询价/合作”与“当前询价/合作需求”。当前需求读取有证据的最新有效状态，避免 OR 永久累积。
3. 支持明确身份更正，例如“这次是个人旅行，不代表公司”；人工已确认值遇到冲突时走复核流程。
4. 复用现有事实历史和版本，记录前值、后值、操作、来源消息和时间；同消息重复处理不重复应用操作。
5. 评分从当前事实重新计算，保存本次分数变化原因。暂不引入未经标注验证的时间衰减公式或自动学习权重。

建议改动：conversation_memory.py、conversation_llm.py、conversation_service.py、schemas/conversation.py、conversation_store.py 与对应回归测试。

验收：想定制→不需要定制、合作咨询→个人旅游能够更新；想定制→补充人数不会清除旧需求；假设句和引用他人话语不会误撤销；重复消息与并发更正结果稳定；保留原有“谢谢不清空需求”的正例。

回退：先影子计算新旧差异；异常时关闭自动状态提升并转人工。已确认的客户更正继续有效，不能通过回退恢复已知错误事实。

### P0 05 约束关键业务声明

目标：阻止“引用正确但承诺错误”，并保持普通回答的可用性。依赖：P0-01、P0-02，复用 P0-03。工作量：4–6 人日。

实施：

1. 定义声明类型：产品描述、客户需求、静态条款、报价数字、动态供应状态、预订/付款/发送结果。每类规定允许的权威来源。
2. 价格和动态承诺从已验证业务对象生成。静态付款/取消条款使用经过业务确认的结构化规则或原文保守展示；P0 尚未结构化的条款不交给模型自由改写成确定承诺。
3. 普通解释绑定具体证据；核对数值、单位、适用对象和条件。对“不含→包含”“预计→保证”“预算→售价”“可申请→已批准”设置有意义的反例与合法近邻。
4. 在自由文本前生成回复计划，明确允许事实、待确认项、回答范围和下一步问题。输出元数据区分有来源、经规则核验、经人工确认，避免一个 grounded 标签承担所有含义。
5. 验证覆盖最终展示文本，不能信任模型自行填写的声明类型。承诺藏在普通解释、或被误标为产品描述，也不能获得已验证标记。金额和执行状态优先使用确定性渲染；其他自由文字未获得足够支持时保持待人工审核，并通过 verification_scope 逐项说明实际验证范围。语义评审模型用于辅助筛查，不是唯一保障。
6. 中文与英文共享关键事实和声明计划；涉及金额、日期、包含项、取消条件和承诺强度时增加一致性检查。

建议改动：conversation_llm.py、openai_recommendation_generator.py、recommendation_builder.py、conversation_reply_composer.py；建议新增 services/claim_evidence.py，并连接现有 quotation.py 与审核状态。

验收：引用“价格依人数和酒店而定”不能生成“预订已确认”；覆盖声明类型故意误标、承诺藏在普通解释、数字正确但对象/条件错误等反例；关键承诺挑战集没有未经业务状态支持的声明；合法产品说明和已审核估算仍可展示；同时记录回答保留率和误拒绝率，不能用全部空模板通过验收。

回退：关闭新自由生成分支，使用保守模板及现有审核入口；不取消关键声明限制。

### P0 06 可观测性与受控试点

目标：能解释一次错误来自哪一步，并区分工程成功与业务正确。依赖：设计从 P0-01 开始，最终接入 P0-03 至 P0-05。工作量：3–4 人日。

实施：记录运行与业务对象 ID、事实验证结果、待确认原因、证据版本、生成/回退原因、分阶段耗时和可获取的模型用量。没有用量信息时记 unknown，不当成零成本。普通日志不复制客户原文、邮箱和凭据，通过受控记录 ID 追溯。复用现有审核，增加低负担反馈：采用、修改、拒绝，以及事实错误/资料不足/文风调整等原因。

发布步骤：离线回归 → 脱敏历史回放 → 抽样影子运行 → 内部人工审核试点。影子运行结果不写业务 CRM、不触发外部动作，并设置调用预算。每阶段保存相对基线的收益与退化。

建议改动：observability.py、conversation_service.py、现有 workflow_events、配置、评测报告与部署文档。P0 使用现有日志和数据存储即可，专用观测平台不是前置依赖。

验收：可从问题回复追溯事实、证据、版本和退出原因；超时、无答案、冲突、撤回和不支持证据有准确分类；指标有分母；可以停用新生成能力并保留人工操作和审计记录。

### P0 发布门槛

- 六项任务有代码/文档变更及验收证据；本次三个隔离反例被正确处理，合法近邻仍可完成。
- 原有静态检查、离线测试、覆盖率门槛及适用的 PostgreSQL/Docker 检查通过。新增迁移必须在测试 PostgreSQL 上验证，跳过不能计为通过。
- 首批 80–120 个场景形成可复现报告，既包含正常样本也包含边界挑战；真实业务样本与合成样本分别报告。独立盲测样本不用于调提示词。
- 关键承诺挑战集中的未经支持承诺为零；这只描述该验收集，不宣称生产零错误。
- 有可回答成功率、误拒答、字段准确度、人工修改和延迟/成本基线。真实标注或模型盲测未完成时，仅发布内部候选版，不标为已验证业务质量的正式试点版。

## 4 P1 商机方案和报价闭环

P1 发布目标：在一个明确目的地和客群中，销售可以管理一笔独立商机，获得满足约束的候选方案、带依据和版本的报价，并跟踪下一步与结果。先使用受控维护的产品和价格资料，供应未确认时明确展示未知。

### P1 01 商机与需求版本

目标：避免同客户、不同团期、不同渠道的信息串联错误。依赖：P0 当前事实契约及迁移基线。工作量：4–6 人日。

实施：

1. 新增 Account、Contact、Opportunity 和 RequirementSnapshot 最小模型，为现有会话增加可空的商机关联，支持渐进迁移。
2. 一个商机对应独立出行需求；不同团期默认不自动合并。原有 account_id 的渠道账号含义与新业务企业账户分开命名，避免把渠道账号当客户企业。
3. 需求快照包含当前有效字段及其来源，并记录版本。旧记录可以先一会话映射一商机，再由销售确认合并，不依赖同邮箱自动跨团组合并。
4. 合并/拆分保留旧 ID、来源和历史，并支持撤销。初期模糊匹配只提示候选，不能静默自动合并。
5. 旧会话接口通过新的契约兼容层继续工作；新商机接口在响应中明确当前需求版本。根据版本进行并发更新检查，阻止静默覆盖。

建议改动：新增 domain 或 schemas 下的商机/需求类型与服务；扩展 conversation_store.py、api/main.py、Alembic 迁移、CRM 映射和对应 API 测试。业务服务与存储访问分离，但不要求同时重构所有旧模块。

验收：同旅行社的两个并行团组互不串数据；同商机跨渠道关联有证据；重复消息不重复创建需求版本；旧会话仍可读和处理；能够从方案/报价回溯对应需求。

回退：使用兼容的新增字段和表；关闭新商机入口仍可读取旧会话。已产生的新商机与需求历史保留，不通过删除表或数据库降级回退。

### P1 02 产品目录和供应数据契约

目标：把产品能力、供应确认和价格规则分开，建立可维护的数据权威。依赖：P1-01。工作量：4–7 人日；业务资料整理另计。

实施：

1. 首期选择一个目的地、一类团组，维护 3–5 个可审核的产品/方案组件。支持结构化文件导入或简易维护页，记录编辑者和来源。
2. 产品记录目的地、时长、季节、客群、容量、包含/不含服务；逐项声明硬约束、可定制条件和偏好。不能将所有条件都默认设为可放宽。
3. 供应记录指定日期/团组的 confirmed、unavailable、unknown 状态、确认人、来源与过期时间。产品手册中的“提供英语导游”不能代替指定团期的资源确认。
4. 价格规则记录版本、币种、计价单位、适用日期/人数/酒店、附加费和来源。沿用现有 Decimal 引擎；没有业务确认规则时仅提供待核价方案。
5. 知识正文记录发布状态、有效期和适用范围。草稿资料与正式资料分开，停用或过期不物理删除历史引用。

建议改动：产品目录 schema、目录加载/校验服务、quotation.py、知识元数据与配置、导入检查；复用现有知识快照和价格规则，不把文本向量库当作实时库存数据库。

验收：过期规则不参与当前正式核价；容量冲突、价格缺失和供应未知分别报告；修改目录/价格不改变历史报价；包含项和排除项均有来源；错误导入返回定位信息而不部分污染正式目录。

回退：保留上一个已发布目录/价格版本；停止新版本用于新报价。已批准且仍有效的报价按既定业务流程处理，不能用回滚目录悄悄改价。

### P1 03 约束推荐与报价版本

目标：推荐结果说明可行性和取舍，报价可复算、可追溯。依赖：P1-01、P1-02、P0-05。工作量：4–7 人日。

实施：

1. 推荐分为硬约束过滤、软偏好排序、证据解释。硬约束已知不满足的方案不能标为可执行；必要信息未知时标为待核实。
2. 输出 1–3 个候选及满足项、冲突项、需调整项和未知项。没有可行方案时解释阻塞点，并提出可以协商的约束；不自动放宽客户明确条件。
3. 预算记录金额、币种和范围，如每人/总额、是否含机票。预算与供应售价分别存储，缺单位不能自动比较。
4. QuoteVersion 绑定需求、产品、价格、规则和供应版本，保留包含项、排除项、假设、币种和有效期。数值由代码计算，模型解释经核验的结果。
5. 需求变化进行影响分析：人数变化触发容量和报价复核；客户姓名拼写更正通常不触发价格重算。受影响报价标记 stale_requires_review，原版本保留。
6. 正式对外报价需要满足发布条件并有审核记录；内部估算继续明确为估算。折扣超范围、资源未确认或条件冲突时进入人工决策。

建议改动：product_recommendation.py、quotation.py、conversation_service.py、草稿/报价 schema、新报价版本存储、审核与 CRM 投影。

验收：明确违反容量、日期等硬约束的方案不进入可执行列表；相同版本输入复算金额一致；中英金额、币种、包含项和有效期一致；客户改人数后旧审核结果不能授权新版报价；找不到可行候选时给出具体原因。

回退：停用自动候选排序或报价生成，保留目录浏览、人工报价和历史版本；不得恢复已过期报价的可执行状态。

### P1 04 销售工作台与下一步任务

目标：销售能在一个商机详情页完成接手、核对、修改、审核和安排跟进。依赖：P1-01、P1-03；P1-05 接入后台状态。工作量：5–8 人日。

实施：

1. 列表按待响应、待补信息、待报价、待供应确认、待客户决定分类，显示负责人、期限和阻塞原因。
2. 详情显示需求快照及变更、候选方案差异、当前报价、供应确认、沟通时间线和下一步动作。技术日志放详情入口。
3. 复用现有草稿编辑、审核、版本和人工发送记录，新增需求/报价差异提示。未经实际渠道回执确认的发送，不标成系统已发送。
4. 追问按销售阶段选择最有价值的 1–2 项；客户已回答的问题不机械重复，未知但与当前步骤无关的字段不阻止展示初步产品。
5. 对空列表、运行中、失败可恢复、证据不足和同步冲突提供明确操作；刷新后恢复状态，未保存编辑有提示。
6. 如果试点有多名操作者，发布前必须有服务端可验证的个人身份、负责人权限和记录隔离。现有共享 operator 身份不能提供个人审计；企业 SSO 可后置，但真实多人身份控制不能后置。

建议改动：web/app.js、workspace.js、index.html、styles.css、商机/任务 API 和 api/access.py。多人认证集成若需外部身份平台，作为额外工作量单列，不假定已经完成。

验收：用相同业务情景对比旧流程的任务时间、错误和页面切换；并发编辑提示版本冲突；移动端与中英文关键内容可读；多人模式下不能读取或修改无权访问的记录。现有浏览器验收场景继续运行。

回退：保留旧会话入口；新视图通过开关关闭。新建商机、任务与版本数据不能因界面回退丢失。

### P1 05 后台执行与任务恢复

目标：渠道接收与耗时模型/检索处理分离，继续利用现有幂等和 lease/fencing。依赖：P0 故障边界、P1-01。工作量：3–5 人日。

实施：

1. 新增持久任务与 Outbox 记录，业务接收状态和待执行事件在同一数据库事务中提交。小规模先用 PostgreSQL 任务表及独立 worker 进程。
2. 建议新增 POST /processing-jobs 和 GET /processing-jobs/{run_id}；旧同步接口保持兼容并明确超时。渠道 webhook 按各平台要求在持久化接收后快速确认，不强制所有渠道都使用同一 HTTP 状态码。
3. 状态至少包含 queued、running、waiting_review、succeeded、failed、cancel_requested、cancelled。外部写入结果不明另标 reconciliation_required，不能自动当作普通失败重做。
4. 每一步有预算、最大尝试次数、超时、下次重试时间和错误类别。可重试错误退避；长期失败进入人工异常队列。
5. 同商机状态变更串行化或采用需求版本检查；读取陈旧需求的任务不能覆盖新事实。取消只停止尚未执行动作，已发生副作用如实记录。
6. 各 worker 共享并发/速率限制，保留原有请求、消息和外部操作幂等键。先避免重复执行，再考虑缓存和更复杂编排。

建议改动：API、独立 worker 入口、任务/Outbox 存储和迁移、conversation_store.py、crm_workflow.py、Compose 配置、任务状态 UI。

验收：接收成功但 worker 尚未启动时任务不丢失；进程在各阶段退出可恢复；重复提交关联同一业务任务；模型 429/超时有界重试；CRM 成功后响应丢失进入核对而非重复创建；队列积压可观察；取消后陈旧任务不能写入新结果。

回退：停止接收新异步任务后排空或冻结旧任务，恢复兼容入口。业务数据和执行记录保留；不能同时启用两套执行器处理同一任务。

### P1 06 CRM 字段权属与冲突处理

目标：AI 更新不覆盖销售手工维护信息，同步结果可核对。依赖：P1-01、P1-05。工作量：3–6 人日。

实施：

1. 建立字段权属表，至少区分客户明确需求、销售维护阶段/负责人、系统计算值、AI 推断。共享字段标明冲突优先级。
2. CRM 同步引用本地商机和方案/报价版本，客户企业、联系人和商机分开映射，避免一个客户页面覆盖多个团组。
3. 提交前检查被审核版本是否仍有效；读取远端相对上次同步基线的变化。远端缺少原子条件更新时，说明读后写存在竞争窗口，以字段所有权、局部更新、回读和人工冲突处理收敛。
4. 继续使用已有幂等与 unknown 结果核对机制；区分可安全重试、需要回读和需要人工介入。部分步骤失败不重复已成功副作用。
5. 保存同步差异、冲突原因与处理人；AI 建议不冒充客户确认，不重置销售阶段。

建议改动：notion_crm.py、crm_workflow.py、CRM schema、字段映射文档和测试适配器；真实验证使用测试数据源。

验收：销售在 CRM 修改阶段后 AI 再同步，人工值保留；审批后需求变更阻止旧提案提交；同客户多商机正确对应；限流/超时/部分成功/响应丢失有明确状态；重试不重复创建记录。

回退：暂停写入，保留本地商机处理和只读差异预览；对不确定写入先回读，不能靠新建记录绕过冲突。

### P1 07 销售反馈与指标归因

目标：把人工纠正和真实商机结果变成产品改进依据。依赖：P1-01、P1-03、P1-06。工作量：3–4 人日。

实施：增加业务事件，区分销售认可、实际联系、有效报价、客户接受、供应确认、成交、丢单和取消。使用幂等事件键，关联商机、需求、报价与运行版本。拒绝原因采用少量固定选项加备注；文风修改和事实修改分开。人工耗时先抽样记录，避免强迫销售填写大量表单。

指标可从报表钻取到商机和事件。取消、退款、合并及重复回执可更正统计，保留更正历史。定义转化观察窗口和贡献毛利口径，尚未经过完整观察窗口的商机单列 pending，不当作失败。

建议改动：业务事件存储、反馈 API、工作台反馈入口、聚合报表与指标字典。复用 workflow_events 的适用部分，但运行错误和商业结果用不同事件类型。

验收：重复回传只计一次；每个报表数字可追溯；同商机不同版本不会重复计算成交；取消与合并正确修正；能够分渠道、客群、语言和版本查看结果。

回退：关闭自动聚合，保留原始结果事件和人工查看；不删除已记录的业务标签。

### P1 分批交付与发布门槛

P1-A 完成商机、需求和目录；P1-B 完成约束推荐、版本报价及主要工作台；P1-C 完成后台执行、CRM 冲突与反馈集成。后台任务和观测可以在 P1-A 后并行开发，正式接入仍需通过整体故障验收。

发布门槛：一个试点客群的真实完整流程可完成；目录/价格由业务确认；需要人工核实的供应始终标明；迁移和恢复在 PostgreSQL 测试库验证；CRM 测试数据源联调通过；多人试点有真实个人身份与权限；实际采用率和人工耗时可测。尚缺供应或价格资料时，可以验收架构和待确认流程，但不能宣称报价业务可正式上线。

## 5 P2 通过实验优化质量成本和人效

P2 以 P0/P1 的真实基线和结果标签为输入。每次实验只改变一个主要因素，预先确定质量不下降的可接受范围，保留当前稳定版本作为对照。

### P2 01 扩大盲测与校准门槛

依赖：P1-07。工作量：3–5 人日，标注工时另计。

从销售纠正、拒绝和客户更正中整理 300–500 个代表性业务案例；另建挑战集，分别报告。按客户与时间隔离调优集和最终盲测集。同客户近似问题、同对话轮次不得分散到训练/调优与测试中。对存在争议的关键样本由两名业务评审者裁定；只有一人时保留争议标记，不冒充共识标签。

交付：数据版本、标注指南、分层报告、风险覆盖曲线和发布门槛。自动处理覆盖率与接受部分错误率成对展示，防止通过大量转人工提高表面准确率。验收：可以复现分层结果；阈值在校准集选取后锁定；盲测仅在发布候选确认时运行；没有足够独立样本的指标明确不可下结论。

### P2 02 检索和证据覆盖实验

依赖：P2-01、P1-02。工作量：3–5 人日。

以现有 BM25+BGE-M3+RRF 为基线，比较现有重排器的在线接入、Qwen3 文本 embedding/reranker 和必要的上下文增强。固定知识快照、召回预算与生成模型，先测检索再测完整回复。查询需带当前有效需求，旧目的地或撤回条件不能污染检索。候选数、证据数量按问题维度验证，不机械把三个片段当所有问题的足够证据；若扩展证据上限，统一修改 schema、提示词、接口、前端和评测契约。

交付：逐题对照、facet recall、无答案表现、语义支持率、P95 和成本。检索数据随目录版本增量发布，缓存键绑定知识版本。验收：在固定质量约束下至少改善一项业务相关指标，收益超过样本噪声且没有关键分层退化；否则保留 BGE 基线。价格、权限和供应有效性仍由结构化查询控制，不由相似度决定。

### P2 03 模型路由与上下文预算

依赖：P2-01，复用 P2-02 结论。工作量：3–6 人日。

分别为确认短语、简单字段、常规回复、复杂冲突建立执行路线。规则可解决的跳过模型；轻量模型失败或证据冲突时才升级。候选模型先与当前模型在相同来源和预算下盲测。上下文优先保留当前需求、未解决问题、最近已发送内容和必要证据，避免完整历史持续膨胀。

缓存只能用于条件相同的可复用结果，键包含权限/组织范围、需求版本、知识版本、模型与提示词版本；供应确认和报价不能使用过期语义缓存。运行中关键版本固定，不把旧规则和新规则混为一次结果。

交付：路由规则、升级原因、预算配置、成本和延迟对照。验收：关键质量指标满足预先约定的非劣标准，并确实降低每个有效推进商机的总成本或延迟。回退：逐路线关闭新模型，恢复已验证基线，保留实验结果。

### P2 04 跟进优先级与下一步建议

依赖：P1-04、P1-07、P2-01。工作量：3–5 人日。

先基于当前阻塞点、响应期限、客户最近行为、准备程度和销售容量改进规则排序。客户适配、购买信号、准备程度和信息可靠性分别展示。前 K 条的 K 对应销售实际每天可处理的数量；与旧 PolicyV1 排序比较，而不是只看总分变化。

有足够成熟标签后，可以比较简单逻辑回归或树模型；概率校准使用独立数据，并控制同客户/时间泄漏。未被销售跟进的线索通常缺少真实结果，不能直接标为无价值。样本或结果窗口不足时交付规则与数据报告，暂缓学习模型。

验收：离线 Precision@K/Lift@K 和小范围实际推进量可核对；记录建议拒绝原因；重复追问与无效打扰不增加；业务 A/B 按客户或销售归属隔离并等待相同观察窗口成熟。无法证明收益时保留旧排序。

### P2 05 知识刷新和运营可靠性

依赖：P1-02、P1-05、P1-06。工作量：3–5 人日。

建立资料发布、更新、停用和有效期流程。知识变更后识别受影响的商机/报价，仅重算相关对象；过期供应不自动沿用。完善运行看板：排队时间、阶段耗时、未知外部提交、同步冲突、单位有效商机成本和人工复核积压。

交付：增量索引发布/回滚、告警与异常处理说明、备份恢复演练记录、压测报告。固定测试硬件、并发、输入长度、知识规模和缓存条件后，分别测试冷启动、常态和供应商故障。验收：可定位业务影响范围；备份能恢复并验证记录数/版本关联；高并发和限流时系统有界排队，不能无界重试；达不到既定负载预算时先限流再扩容。

## 7 实施前统一的契约

这些是建议契约，需要在对应 PR 中定义为实际 schema 和接口。新增文件名可以调整，行为边界必须保持一致。

### 7.1 关键数据契约

| 对象 | 最小字段或关系 | 必须成立的约束 |
| --- | --- | --- |
| FactCandidate | field、proposed_value、raw_quote、quote_span、source_message_id、operation、extractor_version、verification_status | 来源存在且属于当前授权商机；未核验候选不覆盖已确认值 |
| FactOperation | set/replace/retract/pending、previous_version、source、actor、idempotency_key | 未提及不更新；显式撤回有证据；重复消息只作用一次 |
| RequirementSnapshot | opportunity_id、version、facts、created_at、changed_fields | 历史不可被新需求覆盖；所有字段来源可追溯 |
| Claim | type、value/text、evidence_refs、verification_method、business_version | 数字、单位、对象、条件一致；动态承诺来自业务状态 |
| Proposal | requirement_version、catalog_version、candidates、hard_failures、unknowns、tradeoffs | 已知硬约束失败不得标为可执行；未知不得当满足 |
| QuoteVersion | requirement/catalog/price/rule/supply refs、currency、items、total、assumptions、valid_until、review_status | 金额由代码复算；需求或关键来源变化使相关审核失效 |
| ProcessingJob | run_id、business_key、stage、state、attempts、retry_at、lease、input_versions、budget | 外部副作用幂等；旧版本任务不能覆盖新状态；重试有上限 |
| OutcomeEvent | event_id、opportunity_id、outcome_type、occurred_at、source、related_versions、supersedes | 重复事件不重复计数；结果更正保留历史 |

quote_span 的字符计数规则在服务端和前端统一，覆盖中文及包含 emoji 的消息；原文定位失败时不能伪装成精确引用。来源真实存在也不证明来源内容正确，仍需要业务适用性、时效和权威性判断。

### 7.2 需求与报价状态转换

| 触发事件 | 要求 |
| --- | --- |
| 客户补充缺失字段 | 生成新的有效需求版本，记录增加的字段 |
| 客户明确更正或撤销 | 原事实进入历史，当前值更新或撤回；按影响范围重新评估 |
| 客户未提及已有字段 | 保持当前值，不能因默认 false 清空 |
| 客户修改影响报价的字段 | 旧报价保留，当前适用状态转为待复核；旧批准不能授权新版 |
| 新价格/供应资料发布 | 标出受影响对象；是否重算已批准报价由业务条款决定，不能静默改价 |
| 两名销售同时编辑 | 后提交者收到版本冲突，显示差异，不自动覆盖 |
| CRM 调用超时但可能成功 | 标记待核对，按幂等业务键回读；没有证据时不再次创建 |
| 退订或关闭商机 | 按现有抑制规则阻止后续外部跟进；允许经授权查看历史 |

### 7.3 API 兼容与迁移

旧 /process-lead、/conversations/messages 和既有草稿审核接口先保留。P1 新增商机、需求版本、报价和任务接口；当响应需要变化时增加可选字段或明确版本化，更新前端、n8n 契约和示例。同步变异行为不能用同一路径悄悄改成只返回任务编号。

数据库采用新增兼容字段/表、双读兼容、分批回填、验证再切换的步骤。历史数据不能可靠推断的字段保持 unknown 或 legacy_unverified。先对测试数据库备份副本演练，验证历史会话数、引用、草稿和报价关联；应用回退仍能读取已经写入的数据。回退优先切换应用或功能开关，不默认数据库降级。

报价和 CRM 动作在提交时再次检查目标记录、需求/草稿版本、权限与审批状态。日志记录检查结果和简短理由，不需要存储模型内部推理过程或完整敏感消息。

### 7.4 读写兼容与最小部署门槛

功能开关回退不等于可以启动任意旧程序。记录数据库 schema 版本、事实/需求契约版本和最低 writer 版本，执行器启动及任务恢复时检查兼容性。

| 情况 | 允许行为 |
| --- | --- |
| 新 schema 已扩展，旧程序仅阅读且字段兼容 | 可只读查看，隐藏无法理解的编辑操作 |
| 新 schema 已启用 retract 或商机需求版本，旧程序不理解 | 禁止旧程序写入；通过新契约兼容层编辑，或保持只读 |
| 停用新生成器但保留新事实/版本服务 | 可回退为保守模板，客户已确认的更正仍有效 |
| worker 或任务的输入版本落后于当前业务版本 | 重新读取并受控重算，或进入人工复核，不能覆盖新状态 |

部署验收加入旧 worker 未退出、旧任务重放、关闭新功能后更正仍有效三类案例。先扩展兼容结构，再切换写入者，最后在另一个版本清理旧结构；不要同时启用绕过新契约的旧写入路径。

任何非本机访问的试点，包括单人使用，均先验证服务端认证、对象访问权限、渠道验签、TLS/反向代理配置、请求限额和凭据管理；任务查询、只读接口和写接口都纳入检查。现有保护与访客隔离能力复用并验收，企业 SSO 和多租户平台不作为默认前提。

第一次使用真实数据或执行业务数据库迁移之前，完成最小备份恢复验证；P2-05 再进行系统化容量和灾难恢复演练。演示访客与业务数据保持隔离，禁止以公开演示模式承载实际客户工作流。

## 8 数据与验收指标

### 8.1 数据准备节奏

P0 先用约 80–120 个场景建立验证框架；P2 在真实反馈基础上扩展到 300–500 个代表性案例，另建挑战集。数量为规划范围，关键是覆盖和独立性；大量同一客户改写不能代替独立客户样本。

最低覆盖包括：首次询盘、普通补充、短答与确认、明确更正、撤回、身份变化、两团并行、跨渠道关联、预算单位、日期歧义、供应未知、硬约束失败、部分答案、无答案、冲突资料、过期条款、双语承诺一致、重复消息、任务中断和 CRM 结果不确定。

业务真实样本、人工编写样本、模拟模型反例分别标记。评测保存每轮预期有效事实、允许回答范围、必须待确认内容、禁用声明、预期状态与外部动作；不强迫合法答案必须逐字匹配一个模板。

### 8.2 指标字典与初始目标

以下目标需在 P0 基线后由业务和开发共同确认。报告同时列分子/分母、样本来源、版本和不确定性；挑战集结果不冒充生产发生率。

| 指标 | 定义 | 建议使用方式 |
| --- | --- | --- |
| 关键事实精确率 | 正确且语境/单位/对象一致的输出关键字段数 / 输出关键字段数 | 初始试点目标 ≥98%；按人数、日期、预算等字段分开报告 |
| 关键事实召回率 | 正确抽出的可获得关键字段数 / 标注可获得关键字段数 | 初始目标 ≥95%；与精确率并看，避免大量留空 |
| 当前状态正确率 | 最终有效事实和意图全部符合标注的会话数 / 评测会话数 | 初始目标 ≥98%；更正/撤回另报，检查逐轮状态 |
| 声明证据支持率 | 来源真正支持且适用的声明数 / 需要证据的声明数 | 初始目标 ≥98%；关键承诺挑战集出现错误即阻止放量 |
| 无答案错误作答率 | 无答案场景中给出无依据实质答案数 / 无答案场景数 | 与可回答成功率和不必要拒答率同时报告 |
| 硬约束违反率 | 明确违反已知硬约束却标为可执行的方案数 / 标为可执行的方案数 | 冻结关键验收集为零；未知条件披露另测 |
| 推荐采纳率 | 销售认为有用并采用的方案数 / 实际评审方案数 | 不与未经修改采用率混用；记录不采用原因 |
| 人工处理时间 | 阅读、纠错、审核与操作的实际时间 | 同类案例配对比较，试点争取中位数下降 30% |
| Precision@K 和 Lift@K | 前 K 商机中的有效结果比例，及其相对基线提升 | K 对应销售容量；仅统计结果窗口成熟且口径一致的样本 |
| 系统完成与恢复 | 成功完成/恢复的任务数 / 应完成/应恢复任务数 | 副作用重复与未知结果分别统计，不能仅以 HTTP 200 判断 |
| 响应延迟 | 持久化接收时间、排队时间、首个可用草稿时间 | 分别报告 P50/P95；普通路径可先试验受理 1 秒、首稿 P95 20 秒预算 |
| 有效商机成本 | 模型、搜索/采集、基础设施分摊和人工成本 / 被销售认可且实际推进的去重商机数 | 质量门槛满足后优化；未推进及失败任务成本也进入分子 |
| 主业务指标 | 销售认可且推进到定义明确的下一阶段的商机数 / 销售投入工时 | 试点主指标；阶段定义固定，避免人为拆阶段提高数值 |
| 长期业务指标 | 归因窗口内成交贡献毛利 / 销售投入工时 | 同时看每条合格入站线索的转化；取消/退款按业务口径回算 |

98% 等数值是工作目标，不代表现有项目能力，也不是用几十条样本即可证明的可靠性。关键分层样本太少时只报告观察结果和区间，继续人工审核，不把总体平均掩盖某一语言或渠道的明显退化。

### 8.3 可复现性能和成本实验

固定并记录 CPU/内存/数据库、模型标识、供应商、输入长度分布、会话轮数、知识规模、候选与证据上限、缓存状态和测试时间。先用规则/模拟供应商测试 1、5、10 并发级别的队列与数据库行为，再在费用预算内测试真实模型。模拟延迟不能当作真实模型端到端延迟。

分别测试正常运行、冷启动、429、超时、重试与 worker 重启。交互式草稿和需要外部研究的长任务分开计时。若真实模型测试次数不足，P95 仅作探索结果；增加样本后再制定 SLO。优化不能通过隐藏失败、删除人工处理成本或缩小困难样本获得表面收益。

### 8.4 业务试点与放量

1. 历史脱敏回放：验证事实和回复，不产生业务写入。
2. 影子比较：对抽样输入同时得到基线和候选结果，仅对内部评审可见。
3. 人工审核试点：在固定客群中使用，通过审核和业务流程后才产生获授权的 CRM 操作。
4. 小范围对照：按客户或销售归属分组，预先确定指标、观察窗口及停止条件，避免同客户同时受到不同策略影响。
5. 放量：真实收益和关键质量达标后扩大；关键无依据承诺、跨客户数据混用或重复外部副作用出现时立即停止对应自动分支，核对受影响记录。

这些是产品实施中的试点授权边界，不代表本次对话已经执行了外部调用或数据写入。
